The Certified Kubernetes Application Developer (CKAD) exam is a hands-on, performance-based test where you solve real-world scenarios on live Kubernetes clusters rather than answering multiple-choice questions.

To help you practice effectively, here are 20 realistic, scenario-based challenges designed to mimic the complexity, domains, and tasks you will face in the actual Linux Foundation exam.

### Domain: Application Design and Build (20%)

#### Scenario 1: Multi-Container Pod (Design Patterns)

* **Task:** Create a Pod named `analytics-processor` in the `default` namespace. The Pod should contain a primary container running the image `busybox:1.36` that executes the command `sh -c "while true; do date >> /var/log/analytics/data.log; sleep 5; done"`. Add a second **ambassador** container running `redis:7-alpine` that exposes port `6379`.
* **Storage:** Use an `emptyDir` volume named `log-volume` mounted at `/var/log/analytics` only for the primary container.

#### Scenario 2: Build a Container Image Optimization

* **Task:** You are handed an unoptimized application layout. Write a multi-stage `Dockerfile` that:
1. Uses `golang:1.21-alpine` as the builder stage to compile a binary from a local `main.go`.
2. Copies only the compiled binary into a minimal `distroless/static` or `alpine:3.19` final image to minimize the attack surface.
3. Ensures the application runs as a non-root user (UID `10001`).


* *(Note: On the real exam, you might build this using `docker` or `podman` on the node).*

#### Scenario 3: Jobs and CronJobs with Resource Limits

* **Task:** Create a CronJob named `database-backup` in the `ops` namespace.
* **Schedule:** It must run every night at midnight (`0 0 * * *`).
* **Spec:** The job should run a container using `postgres:16-alpine` executing `echo "Backup Complete"`. It must retain a history of at most `3` successful executions and `1` failed execution.
* **Resources:** Define a CPU request of `100m` and a memory limit of `250Mi`.

#### Scenario 4: InitContainers for Readiness Dependency

* **Task:** Create a Pod named `frontend-app` using image `nginx:alpine`.
* **Requirement:** The application container must wait for an external service named `cache-db` to be reachable on port `6379` before it starts.
* **Implementation:** Implement an `initContainer` named `init-cache-check` using the `busybox:1.36` image that loops running `nc -zvw3 cache-db 6379` until successful.

### Domain: Application Deployment (20%)

#### Scenario 5: Rolling Updates and Rollbacks

* **Task:** There is an existing Deployment named `webapp-deployment` in the `production` namespace.
* **Action 1:** Update the container image of this deployment to `nginx:1.25.3`. Monitor the rollout until it successfully completes.
* **Action 2:** Check the rollout history. Undo the latest deployment to safely rollback to the previous stable container image version due to an application bug.

#### Scenario 6: Blue-Green Deployment Routing

* **Task:** You have two identical Deployments running in the `traffic` namespace: `app-blue` (running version 1) and `app-green` (running version 2). A Service named `app-service` is currently routing traffic to the `blue` version.
* **Action:** Modify the Service's selector configuration so that it instantly cuts over all live user traffic to target the `green` version instead.

#### Scenario 7: Deployment Scaling and HPA

* **Task:** Create a horizontal pod autoscaler (HPA) named `api-scaler` for an existing Deployment named `api-service` in the `backend` namespace.
* **Parameters:** Set the minimum replica count to `2` and the maximum to `8`. Trigger autoscaling when the average target CPU utilization across all pods reaches `75%`.

### Domain: Application Observability and Maintenance (15%)

#### Scenario 8: Liveness and Readiness Probes

* **Task:** Configure a Pod template or modify an existing Deployment named `health-check-demo` to include proper probes:
* **Readiness Probe:** An HTTP GET request on path `/ready` on port `8080`. Start checking after an initial delay of `10` seconds.
* **Liveness Probe:** An HTTP GET request on path `/live` on port `8080`. Run the check every `5` seconds.



#### Scenario 9: Extracting Container Logs

* **Task:** A multi-container Pod named `order-manager` in the `finance` namespace is throwing errors.
* **Action:** Inspect the logs specifically for the container named `payment-gateway`. Filter out lines containing the string `"ERROR"` and save those extracted log lines into a host file located at `/opt/errors/payment_failed.txt`.

#### Scenario 10: Debugging and Fixing a Failing Pod

* **Task:** A Pod named `data-ingestor` in the `processing` namespace is stuck in a `CrashLoopBackOff` state.
* **Action:** Diagnose the root cause using cluster tools (e.g., event stream or container termination messages). Fix the underlying configuration issue (such as a missing environment variable or wrong entrypoint command) directly in the template to bring the Pod to a stable `Running` state.

### Domain: Application Environment, Configuration, and Security (25%)

#### Scenario 11: ConfigMaps and Environment Variables

* **Task:** Create a ConfigMap named `app-settings` in the `config` namespace containing the key-value pair `DB_HOST=cluster-db-uri`.
* **Consumption:** Create a Pod named `backend-worker` using the `alpine` image. Inject the value of `DB_HOST` from the ConfigMap as an environment variable named `DATABASE_URL` inside the container.

#### Scenario 12: Secrets Mounted as Volumes

* **Task:** Create a Secret named `api-credentials` containing an API key (`api-key=supersecret123`).
* **Consumption:** Mount this Secret as a read-only volume inside a new Pod named `secure-processor` at the directory path `/etc/api-secret`. Ensure the file permissions are tightly restricted.

#### Scenario 13: Container Security Context (Non-Root & Read-Only Root)

* **Task:** Deploy a Pod named `hardened-nginx` using the `nginxinc/nginx-unprivileged:alpine` image.
* **Security Context Requirements:** 1. Configure the Pod security context to run all containers with user ID `101`.
2. Configure the container security context to enforce a completely read-only root filesystem (`readOnlyRootFilesystem: true`).
3. Allow an exception by mounting an `emptyDir` volume to `/tmp` so Nginx can write its cache files safely.

#### Scenario 14: NetworkPolicies for Microservice Isolation

* **Task:** Create a NetworkPolicy named `allow-db-access` in the `secure-zone` namespace.
* **Rule:** It must protect pods matching the label `role: database`. It should only permit incoming (Ingress) TCP traffic on port `5432` from pods that carry the specific label `role: backend-api`. Block all other cross-pod ingress traffic to the database.

#### Scenario 15: ServiceAccounts and RBAC Tying

* **Task:** Create a ServiceAccount named `deploy-operator` in the `default` namespace.
* **Action:** You must ensure that any Pod running with this ServiceAccount has permission to `get`, `list`, and `watch` Deployments within its own namespace. Create the necessary specialized local RBAC `Role` and `RoleBinding` to fulfill this requirement.

### Domain: Services and Networking (20%)

#### Scenario 16: Exposing Applications via Services (ClusterIP vs NodePort)

* **Task 1:** Create a ClusterIP Service named `internal-service` that exposes an existing deployment group labeled `app=internal-core` on port `8080` targeting container port `80`.
* **Task 2:** Create a NodePort Service named `external-access` that exposes a deployment group labeled `app=frontend-ui` on port `80`, map it to target port `80`, and explicitly bind it to NodePort `32080`.

#### Scenario 17: Ingress Controller Resource Routing

* **Task:** Create an Ingress resource named `main-ingress` in the `web` namespace.
* **Rules:** Configure routing rules using the host `app.example.com` such that:
* Traffic aimed at path `/api` is routed to the backend service named `api-service` on port `8080`.
* Traffic aimed at path `/` (root) is routed to the frontend service named `frontend-service` on port `80`.



#### Scenario 18: PersistentVolumes and PersistentVolumeClaims

* **Task 1:** Create a PersistentVolume named `pv-local-storage` with a capacity of `2Gi`, access mode `ReadWriteOnce`, and hostPath storage mapping to `/mnt/data`.
* **Task 2:** Create a PersistentVolumeClaim named `pvc-app-claim` requesting `1Gi` capacity with matching access modes so it binds successfully to the PV.
* **Task 3:** Mount this PVC to a new Pod named `storage-test-pod` under the directory `/data`.

#### Scenario 19: CoreDNS/Kube-DNS Resolution Architecture

* **Task:** A front-end application container inside your cluster needs to perform an internal look-up for a service named `payment-processor` located inside a completely separate namespace called `transactions`.
* **Action:** Write down or configure the precise Fully Qualified Domain Name (FQDN) format inside your application config file to ensure correct cross-namespace DNS service resolution.

#### Scenario 20: Utilizing StorageClasses for Dynamic Provisioning

* **Task:** Create a PersistentVolumeClaim named `dynamic-pvc` in the `default` namespace.
* **Requirements:** Do not map it manually to a static PV. Instead, configure it to request `5Gi` of space using a cluster-provided StorageClass named `fast-storage` to dynamically handle volume provisioning on demand.

### 💡 Tips for the Practical CKAD Exam:

1. **Get Comfortable with `kubectl` Imperative Commands:** Don't write YAML from scratch. Use commands like `kubectl run ... --dry-run=client -o yaml > pod.yaml` and modify them. This saves vital time.
2. **Context Switching:** Always make sure you execute the `kubectl config use-context ...` command if it's provided at the top of a scenario question so you don't build resources in the wrong cluster.
3. **Use Short Names:** Save keystrokes by using short names like `po` (pods), `deploy` (deployments), `cm` (configmaps), `sec` (secrets), `netpol` (networkpolicies), and `pvc` (persistentvolumeclaims).
